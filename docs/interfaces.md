# TrickOrBot 인터페이스 명세

이 문서는 팀 공통 규격을 확정할 자리입니다.
아래 내용만으로 토픽 이름이나 메시지 필드가 확정된 것은 아닙니다.

## 작성 순서

1. 관련 파일의 역할과 현재 장비 토픽을 확인합니다.
2. 필요한 메시지 필드와 토픽·서비스 이름을 정의합니다.
3. 발행자와 구독자 담당자가 같은 규격을 사용합니다.
4. 규격이 정해진 후 해당 노드의 코드를 구현합니다.

## 각 통신 항목에 적을 내용

- 이름과 토픽·서비스·액션 구분
- 메시지 타입과 필드 의미
- 발행·제공 노드 및 구독·호출 노드
- 단위와 좌표계
- 시각의 의미: 촬영 시각, 발행 시각, 수신 시각 중 무엇인지
- 필요한 발행 주기와 QoS
- 빈 결과, 유효하지 않은 값, 오래된 데이터의 표현
- 연결 단절 시 수행할 동작

## 공통 구현 범위

- 위치와 속도 등은 적합한 기존 ROS 메시지를 우선 사용합니다.
- 프로젝트 전용 데이터만 tob_interfaces 메시지로 정의합니다.
- 게임 판정은 tob_game 한 곳에서 확정합니다.
- 부우 행동에는 관측 가능한 정보만 사용합니다.
- 웹캠 제보와 부우 카메라 직접 관측을 구분합니다.
- 실물·시뮬레이션의 시각 기준을 맞추고 서로 다른 시계를 직접 비교하지 않습니다.
- 재접속한 웹에는 현재 GameState를 전달합니다.
- 회차 기록은 JSONL로 시작하고 기존 백엔드의 DB 기능을 활용합니다.
- 별도의 이벤트 재생 서버, 메시지 브로커, 범용 플러그인 시스템은 만들지 않습니다.

## 구현 전에 정할 게임 규칙

- 체포 시 즉시 종료인지, 하트가 줄어드는지
- 체포·탈출·시간 초과가 겹쳤을 때의 우선순위
- 일시정지 중 제한 시간과 구역 체류 시간을 처리하는 방법
- 의심 게이지 변화와 수색·순찰 복귀 방식
- 아이템이 관측·추격·게임 시간에 미치는 영향
- 위치·관측이 끊겼을 때 게임 진행 상태를 처리하는 방법
- 운영자 수동 복구의 진입·종료 조건
- 펌킨 자동 복귀 기능을 사용할지 여부

## 구현 완료 판단

공통 규격에 맞는 입출력, 파일별 핵심 동작, 명시한 실패 처리를 확인합니다.
이 범위를 충족한 뒤 요청하지 않은 확장 기능을 추가하지 않습니다.
