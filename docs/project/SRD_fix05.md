## 1. System Requirement Method

- 각 SR(시스템 요구)은 시스템 자원 하나를 고르거나 제한하고 **측정 가능한 사양**을 붙인다. 수량과 성능은 BRD의 결과에서 도출하며 임의로 고르지 않는다. 도출 과정은 §10의 표에 있다.
- 요구는 Measurable·Specific·Achievable·Relevant·Verifiable·Traceable 여섯 가지를 만족하게 쓴다(튜터 피드백). 모든 SR에는 근거 BR(비즈니스 요구)과 검증 방법(§9)이 있다.
- **범위는 BRD v1.5 3장을 따른다**: 인수 필수는 Lv1이다. Lv2~3은 BRD 범위의 목표이며 시간 부족 시 컷할 수 있다(BRD O-06: 배터리 기반 남은 회차 → CCTV 요소 → Lv3 → Lv2 순, Lv1과 관람 화면은 컷하지 않음). 그 밖에 로봇 2대, 3 m × 3 m 아레나(구현 지도와의 차이는 부록 C 11번), 상주 운영자 1명이다. Lv4~5·아이템, 술래 파라미터 편집, 퀴즈·설문 저장은 BRD상 추가 발전이며 부록 A에 설계 참고로 둔다. 리더보드는 닉네임만 표시한다(BRD 7.1).
- **구현 기준 표기(fix05)**: SR 행의 `[현재 구현]`은 2026-10-10 22:10 저장소(브랜치별)에서 확인한 구현이고 `[목표]`는 기존 요구다. 구현이 있는 항목은 구현 값을 먼저 적었다. 구현이 인터페이스 정의서의 범위를 넘는 경우(예: 탈출 체류 대기)는 정의서 기준을 따른다. 구현이 없는 안전·보안 요구는 삭제하지 않고 `[목표]`로 남겼다. 부록 E에 전체 현황표가 있다.
- 이 문서는 달성 결과를 주장하지 않는다. 숫자는 요구(목표)이며, 실측으로 확정할 값은 아래 표기로 구분한다.
- "필수"는 MVP 인수 항목(BRD 8장)에 영향을 주는 요구, "선택"은 시간이 되면 구현하는 요구다.
- 노드·토픽·메시지의 이름과 필드는 팀 인터페이스 정의서가 기준이고, 이 문서는 그 위에서 측정 가능한 사양만 정한다. 둘이 다르면 팀이 확인해 함께 고친다(interfaces.md §1).
- 요구는 **BR ID(BRD v1.5의 BR-C/BR-T/BR-KPI. BRD에 대응 BR이 없는 항목은 BRD 절·UC를 병기)**에서 **SR-nnn(시스템 요구)**로 이어지는 ID로 추적한다. `[확인]`·`[가정]`·`[제안]` 표기와 BRD 항목 요약은 부록 D에 있다.

## 6. Interface Requirements

| Interface | Requirement |
|---|---|
| 로봇 ↔ 게임 서버 | 두 로봇의 위치·상태·배터리 ≥5 Hz. 상태 하트비트(주기적 생존 신호) 손실 판정 ≤1 s(SR-033) |
| 인식 ↔ 술래 제어 | `TargetObservation`(관측 시각, `detected`, 신뢰도·박스, `map_valid`, 지도 목표 위치, 두 로봇 사이 거리). 감지 단계는 `map_valid=false`, 위치 계산 단계가 두 로봇 위치·시각을 검증한 뒤에만 `true`. 술래는 유효한 관측과 마지막 유효 관측(기억)만 사용(BR-12) |
| 게임 관리 ↔ 웹 | `GameState`(주기 발행), `GameEvent`(사건 발생 시), 서비스 `GameCommand`. 웹은 효과·표시만 하고 판정하지 않음(SR-016) |
| 안전 감독 ↔ 이동 명령 게이트 | `SafetyState`(`motion_allowed`, 사유, 유효 시간)를 로봇별로 발행. 만료·미수신이면 이동 차단. 실제 속도 명령은 게이트를 우회하지 않음(SR-030~033) |
| 웹 ↔ 도망자 | WASD 입력 ≥10 Hz, 입력이 0.5 s 없으면 정지(SR-031), 키 입력 → 움직임 시작 ≤300 ms(p95) |
| 도망자 → 플레이어 화면 | 압축 RGB ≥15 fps, 지연 ≤500 ms |
| 플레이어 화면 | **[현재 구현]** 1인칭 영상 + AR + 미니맵(부우 위치 표시) + HUD<br>**[목표]** 1인칭 영상 + 제한된 주변 정보 + 열쇠·시간·결과. 술래 위치는 표시하지 않음(BR-04) |
| 운영자 화면 | 탑뷰에 두 로봇, 시작·중단·초기화·비상정지, 수동 조작 |
| 웹 ↔ 내부 노드 | 웹은 게임 서버를 통해서만 접근하고 로봇 노드에 직접 의존하지 않음 |
| 서버 ↔ DB | 회차 이벤트를 발생 즉시 기록(DB 쓰기 실패는 운영자에게 표시) |
| 웹캠 ↔ 서버 | (용도 확정 시) 타임스탬프가 있는 검출·맵 좌표 이벤트 |

## 11. Boundary to the SDD

SRD는 시스템 자원과 측정 가능한 능력을 정한다. SDD는 이 요소들이 **어떻게** 상호작용하는지를 설명한다: 아키텍처, ROS 노드 배치, 토픽·API 이름, 데이터 흐름, 상태기계(술래 순찰 → 의심 → 추적 → 체포/수색 → 복귀), 배치, 타이밍, 오류 처리, 안전 장치 구현. 이 문서에 나오는 노드·토픽·메시지 이름은 팀 인터페이스 정의서(개발팀장 확정, 기준일 2026-10-10)를 따르며, 인터페이스 정의서에 없는 세부는 `[제안]`이고 SDD가 확정한다.

## 부록 A. 레벨 설정 (SR-013의 파라미터, 설계 참고)

인수 필수는 **Lv1**이고 Lv2~3은 BRD v1.5 범위의 컷 가능한 목표다(BRD O-06). Lv1~3의 제한 시간·술래 속도·게이지 값은 BRD 표 6-1과 일치함을 확인했다. Lv4~5는 BRD상 추가 발전이며 확장 설계 참고이고 새 요소가 레벨마다 하나씩 더해진다. 도망자 최고 속도는 모든 레벨에서 0.2 m/s다(팀 결정으로 웹 구현값을 따름. 발표문서 레벨표는 0.25). 의심 게이지 시간은 "도망자가 1.5 m에서 계속 보일 때 다 차는 시간"이다. (맵 설계 7원칙 절은 2026-10-08 18:00 판 팀 Notion "오전 발표 준비"에서 빠졌다. 이전 내용은 git 커밋 a4baeaa의 팀 Notion 내보내기에 있다.)
