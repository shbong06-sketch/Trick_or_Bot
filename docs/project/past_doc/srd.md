## 1. System Requirement Method

- 각 SR은 시스템 자원 하나를 고르거나 제한하고 **측정 가능한 사양**을 붙인다. 수량과 성능은 BRD의 결과에서 도출하며 임의로 고르지 않는다. 도출 과정은 §10에 있다.
- 요구사항은 Measurable·Specific·Achievable·Relevant·Verifiable·Traceable 여섯 가지를 만족하게 쓴다(튜터 피드백). 모든 SR에 근거 BR과 검증 방법(§9)이 있다.
- **MVP 범위는 BRD 3장을 따른다**: 기본 레벨 1개(Lv1), 로봇 2대, 3 m × 3 m 아레나, 상주 운영자 1명. Lv2~5, 아이템, 리더보드는 BRD 상 선택·후속이며 부록 A에 설계 참고로 둔다(OI-03).
- 이 문서는 달성 결과를 주장하지 않는다. 숫자는 요구(목표)이고, 실측으로 확정할 값은 `[확인]`·`[가정]`으로 구분한다.
- "필수"는 MVP 인수(BA-01~04, 06)에 영향을 주는 요구, "선택"은 시간이 되면 구현하는 요구다.

## 2. System Context

시스템은 실내 아레나에서 움직이는 TurtleBot4 2대(술래 `/robot1`, 도망자 `/robot2`), 온보드 항법·인식 소프트웨어, AI 추론용 PC, 무선 통신, 게임 서버, 운영 데이터 저장소, 브라우저 화면(플레이어·운영자·관람)으로 이뤄진다. 상호작용의 세부는 SDD가 다룬다.

| 외부 요소 | 시스템과의 상호작용 | 경계 |
|---|---|---|
| 플레이어 1명 | 조작석 웹 화면에서 WASD로 도망자를 조작, 1인칭 영상·제한 정보 확인 | 아레나에 들어가지 않는다(BR-01) |
| 관람객·동행인 | 지정 관람 위치에서 실물 추격과 역할·목표·종료 안내를 본다 | 관람 위치 밖으로 나오지 않는다 |
| 상주 운영자 1명 | 시작·중단·초기화·복구·충전, 전체 관제 | 계획 외 지원 인력은 기록한다(BR-17) |
| 아레나·소품 | 판자벽·상자, 호박 머리 코스튬, 바닥 테이프 | 점검된 배치만 사용(BRD 8장) |
| 결제·예약·계정 시스템 | 연결하지 않는다 | 범위 밖(BRD 3.2) |

**ROS 구성(2026-10-08 팀 결정)**: Victus 노트북이 서버 PC(FastDDS Discovery Server + 게임 서버), 나머지 고성능 PC는 클라이언트, `ROS_DOMAIN_ID=2`를 전원 공통으로 쓴다.

## 6. Interface Requirements

| Interface | Requirement |
|---|---|
| 로봇 ↔ 게임 서버 | 두 로봇의 위치·상태·배터리 ≥5 Hz. 상태 하트비트 손실 판정 ≤1 s(SR-033) |
| 인식 ↔ 술래 제어 | 타임스탬프가 있는 검출 결과(맵 좌표, 거리, 신뢰도). 술래는 허용된 관측 정보와 기억 정보만 사용(BR-12) |

## 10. Requirement Derivation (수치를 어떻게 얻었나)

**D1. 회차 시간 예산 (KD-03, 04)** — 회차 점유 6분 = 360 s. Lv1 플레이 240 s + 종료→다음 회차 준비 ≤90 s = 330 s. 남는 30 s에 플레이어 안내(BR-18)와 결과 표시를 넣어야 한다. 안내가 30 s를 넘으면 점유 시간이 늘어난다: 6.5분이면 시간당 60/6.5 = 9.2회로 10회에서 8% 줄어든다.

**D2. 배터리와 회차 수 (SR-001, 037)** — BRD 4.4.3: 운용 2.5시간이면 6분 회차로 25회, 4시간이면 40회. 팀 규칙(50% 하한)을 적용하면 쓸 수 있는 시간이 절반이라 1.25~2시간 → 12.5~20회. 그래서 충전 없이 ≥12회차를 요구한다. 발표문서의 6판(30분) 하한은 이보다 낮아 이 값이 더 엄격하다. 실제 소모량(%/회차)은 시험으로 보정한다.

**D3. 지연 예산 (SR-014, 017)** — 키 입력→움직임 ≤300 ms(p95)는 대략 브라우저→서버 50 + 서버 처리 20 + DDS·Wi-Fi 편도 50 + 로봇 수신·명령 선택 50 + 모터 가속 시작 100 = 270 ms, 여유 30 ms `[제안 배분]`. 영상 ≤500 ms는 촬영 70(15 fps의 1프레임) + 압축 40 + 전송 60 + 서버 중계 30 + 브라우저 디코딩·표시 100 = 300 ms, 여유 200 ms. 배분은 실측으로 고친다.

**D4. 대역폭 (SR-003, 014)** — 도망자 영상 2 Mbps ÷ 15 fps ≈ 16 KB/프레임이다. 640×480 JPEG는 보통 20~40 KB라 15 fps에서 2.4~4.8 Mbps가 되어 예산을 넘을 수 있으므로 해상도·품질을 낮춰 맞춘다. 술래 깊이 원본(640×400×2 B×10 fps)은 약 51 Mbps라 Wi-Fi로 보낼 수 없다. 압축 깊이 또는 낮은 해상도를 쓴다. 합계: 도망자 2 + 술래 ≤8 + 제어·상태 ≈0.5 = 약 10.5 Mbps, 여유 3배로 지속 ≥30 Mbps를 요구한다.

**D5. 탐지·연산 (SR-005, 009)** — 술래 0.22 m/s(Lv5)에 도망자 0.25 m/s가 서로 다가가면 상대 속도 0.47 m/s다. 10 fps이면 프레임당 4.7 cm, 탐지 지연 200 ms 동안 9.4 cm 움직이므로 위치 오차 기준(0.2 m) 안에 든다. "연속 탐지 3 s"(체포)는 프레임 30개다. 프레임별 재현율 0.9에서 3프레임 연속 놓칠 확률은 0.1³ = 0.1%(독립 가정)라, 연속 판정에 **놓침 공백 ≤0.3 s**를 허용해도 공정성이 크게 흔들리지 않는다 `[제안]`. 온보드 Raspberry Pi는 YOLO를 10 fps로 돌릴 수 없어 추론은 PC에서 한다(KD-12). 한 PC에서 두 로봇의 Nav2를 돌리면 성능 문제가 생기므로(튜터 Client Setup) Nav2는 술래만 쓰고, 도망자는 조작 + AMCL만 쓴다.

**D6. 통로 기하 (SR-012)** — 로봇 외경 ≈0.34 m이므로 통로 0.8 m에서 한쪽 여유는 0.23 m이고, AMCL 오차 0.15 m를 빼면 0.08 m만 남는다. 교착 위험(RISK-02)이 커서 0.8 m는 하한이고 ≥1.0 m를 권한다. 3 m × 3 m(지도 60×60 셀)에서 발전기를 서로 1.5 m 이상 떼는 배치는 가능하지만(네 모서리 + 중앙), 중앙 장애물과 겹치므로 Lv1은 3곳(G3~G5)만 쓴다. 판자·상자 배치는 배치도로 먼저 확인한다(OI-04).

**D7. 안전 거리 (SR-032)** — 외경 0.34 m라 중심 간 거리가 0.34 m보다 작으면 이미 겹친다. 최대 접근 속도는 Lv1에서 0.25 + 0.12 = 0.37 m/s, Lv5에서 0.47 m/s다. 정지에 0.5 s가 걸리면 접근 거리는 0.185~0.235 m다. 정지 시작 외곽 간격 0.3 m에서 남는 외곽 간격은 0.065~0.115 m로, 접촉이 없다. 따라서 발표문서의 "거리 <0.3 m"는 **외곽 간격** 기준으로 해석해야 안전하다. 중심 간 거리로 읽으면 이미 접촉한 뒤다.

**D8. 체포 거리와 안전 정지의 충돌 (SR-032, 발표 TR-08)** — 체포 기본값은 0.5 m 이내 3 s 연속 탐지다. 이것이 외곽 간격이면 안전 정지(0.3 m)보다 크므로 체포는 안전 정지 전에 성립한다. 중심 간 거리라면 외곽 간격 0.16 m로 안전 정지가 먼저 걸려 체포 전에 로봇이 멈춘다. 하나로 통일해야 한다(OI-23). 이 초안은 **체포 0.5 m도 외곽 간격**으로 읽는다 `[확인]`. 깊이 센서가 재는 값이 도망자 표면까지의 거리라 외곽 간격에 가깝다.

**D9. 시간 동기 (SR-015)** — 300 ms 기준을 10% 이내로 재려면 장치 간 시간 오차가 ≤30 ms여야 한다. LAN의 chrony는 보통 몇 ms 안이라 ≤20 ms를 요구한다.

**D10. 저장 용량 (SR-020, 021)** — DB는 회차당 약 1 KB + 이벤트 100건×100 B ≈ 11 KB라 1,000회차에 약 11 MB다. rosbag은 압축 영상·상태 합계 약 10 Mbps = 75 MB/분 = 약 4.5 GB/시간이다. 50 GB는 약 11시간 분량이므로 모든 회차를 녹화하지 않고 검증 시험만 녹화한다.

**D11. 복귀 오차의 한계 (SR-036)** — AMCL 오차(0.15 m)가 복귀 허용 오차(0.1 m)보다 크다. 복귀 오차는 AMCL 값이 아니라 **바닥 표식 대비 실측**으로 판정하고, Nav2 목표 허용 오차를 ≤0.05 m로 둬야 한다. 달성이 어려우면 허용 오차를 0.15 m로 완화한다(OI-25).

## 11. Boundary to the SDD

SRD는 시스템 자원과 측정 가능한 능력을 정한다. SDD는 이 요소들이 **어떻게** 상호작용하는지를 설명한다: 아키텍처, ROS 노드 배치, 토픽·API 이름, 데이터 흐름, 상태기계(술래 순찰→의심→추적→체포/수색→복귀), 배치, 타이밍, 오류 처리, 안전 장치 구현. 이 문서의 노드·토픽 이름은 [제안]일 뿐이며 SDD가 확정한다.

SRD: System Requirements Document. SDD: System Design Document. BRD: Business Requirements Document. BR: 비즈니스 요구, SR: 시스템 요구, BA: 인수 항목, KPI: BRD 5장 지표. AMR: Autonomous Mobile Robot. AMCL: Adaptive Monte Carlo Localization. DDS: Data Distribution Service. RTT: Round-Trip Time. p95: 95번째 백분위. 술래(Seeker, `/robot1`): 자율 로봇. 도망자(Runner, `/robot2`): 플레이어가 웹으로 조작하는 로봇(BRD 용어로는 생존자). 회차: 게임 한 판. 외곽 간격: 두 로봇 외곽 사이의 거리(중심 간 거리 − 로봇 외경).
