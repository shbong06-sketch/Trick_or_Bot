## 1. System Requirement Method

- 각 SR(시스템 요구)은 시스템 자원 하나를 고르거나 제한하고 **측정 가능한 사양**을 붙인다. 수량과 성능은 BRD의 결과에서 도출하며 임의로 고르지 않는다. 도출 과정은 §10의 표에 있다.
- 요구는 Measurable·Specific·Achievable·Relevant·Verifiable·Traceable 여섯 가지를 만족하게 쓴다(튜터 피드백). 모든 SR에는 근거 BR(비즈니스 요구)과 검증 방법(§9)이 있다.
- **MVP 범위는 BRD 3장을 따른다**: 기본 레벨 1개(Lv1), 로봇 2대, 3 m × 3 m 아레나, 상주 운영자 1명. Lv2~5·아이템·리더보드는 BRD상 선택 또는 후속이며 부록 A에 설계 참고로 둔다.
- 이 문서는 달성 결과를 주장하지 않는다. 숫자는 요구(목표)이며, 실측으로 확정할 값은 아래 표기로 구분한다.
- "필수"는 MVP 인수 항목(BRD 10장)에 영향을 주는 요구, "선택"은 시간이 되면 구현하는 요구다.
- 노드·토픽·메시지의 이름과 필드는 팀 인터페이스 정의서가 기준이고, 이 문서는 그 위에서 측정 가능한 사양만 정한다. 둘이 다르면 팀이 확인해 함께 고친다(정의서 §1).
- 요구는 **BR-nn(비즈니스 요구)**에서 **SR-nnn(시스템 요구)**로 이어지는 ID로 추적한다. `[확인]`·`[가정]`·`[제안]` 표기와 BRD 항목 요약은 부록 D에 있다.

## 2. System Context

시스템은 실내 아레나에서 움직이는 TurtleBot4 2대(술래 `/robot1`, 도망자 `/robot2`), 온보드 항법·인식 소프트웨어, AI 추론용 PC, 무선 통신, 게임 서버, 운영 데이터 저장소, 브라우저 화면(플레이어·운영자·관람)으로 이뤄진다. 상호작용의 세부는 SDD가 다룬다.

| 외부 요소 | 시스템과의 상호작용 | 경계 |
|---|---|---|
| 플레이어 1명 | 조작석 웹 화면에서 WASD로 도망자를 조작, 1인칭 영상·제한 정보 확인 | 아레나에 들어가지 않는다(BR-01) |
| 관람객·동행인 | 지정 관람 위치에서 실물 추격과 역할·목표·종료 안내를 봄 | 관람 위치 밖으로 나오지 않는다 |
| 상주 운영자 1명 | 시작·중단·초기화·복구·충전, 전체 관제 | 계획 외 지원 인력은 기록한다(BR-17) |
| 아레나·소품 | 판자벽·상자, 호박 머리 코스튬, 바닥 테이프 | 점검된 배치만 사용(BRD 8장) |
| 결제·예약·계정 시스템 | 연결하지 않는다 | 범위 밖(BRD 3.2) |

**ROS 구성 (2026-10-08 팀 결정)**

| 항목 | 내용 |
|---|---|
| 서버 PC | Victus 노트북 = FastDDS Discovery Server + 게임 서버 |
| 클라이언트 | 나머지 GPU PC와 TurtleBot4 2대 |
| 도메인 | `ROS_DOMAIN_ID=2`를 전원 공통으로 사용 |
| 게임 판정 | ROS의 게임 관리 노드(`game_manager_node`)가 사탕 획득·하트 감소·시간 초과·탈출 성공·회차 종료의 **유일한 최종 판정자**다. 웹 서버는 ROS 상태를 중계·저장하고 조작 요청만 전달하며, 브라우저는 판정하지 않는다(정의서 §1, §8) |
| 논리 이름 | 게임 로직은 `/robot1`, `/robot2`가 아니라 논리 이름 `pumpkin`(플레이어 로봇)·`boo`(추격 로봇)와 `/tob/...` 토픽을 쓴다. 실제 로봇 번호·네임스페이스는 실행 설정에서 연결한다(정의서 §4.2) |

## 10. Requirement Derivation (수치를 어떻게 얻었나)

각 행은 "입력 → 계산 → 결론" 순서다. 입력의 가정·결정은 §3에 있다. SR 표의 "§10 ○○"은 이 표의 해당 대상 행을 가리킨다.

## 11. Boundary to the SDD

SRD는 시스템 자원과 측정 가능한 능력을 정한다. SDD는 이 요소들이 **어떻게** 상호작용하는지를 설명한다: 아키텍처, ROS 노드 배치, 토픽·API 이름, 데이터 흐름, 상태기계(술래 순찰 → 의심 → 추적 → 체포/수색 → 복귀), 배치, 타이밍, 오류 처리, 안전 장치 구현. 이 문서에 나오는 노드·토픽·메시지 이름은 팀 인터페이스 정의서(개발팀장 확정, 기준일 2026-10-10)를 따르며, 정의서에 없는 세부는 `[제안]`이고 SDD가 확정한다.

## 부록 A. 레벨 설정 (SR-013의 파라미터, 설계 참고)

MVP 인수는 **Lv1만** 대상이다(BRD 3.1). Lv2~5는 확장 설계 참고이며 새 요소가 레벨마다 하나씩 더해진다. 도망자 최고 속도는 모든 레벨에서 0.2 m/s다(팀 결정으로 웹 구현값을 따름. 발표문서 레벨표는 0.25). 의심 게이지 시간은 "도망자가 1.5 m에서 계속 보일 때 다 차는 시간"이다. (맵 설계 7원칙 절은 2026-10-08 18:00 판 팀 Notion "오전 발표 준비"에서 빠졌다. 이전 내용은 git 커밋 a4baeaa의 팀 Notion 내보내기에 있다.)

| 항목 | Lv.1 | Lv.2 | Lv.3 | Lv.4 | Lv.5 |
|---|---|---|---|---|---|
| 새 요소 | 기본 규칙(열쇠 즉시 획득) | 발전기 체류 + 관문 CCTV | 멈춰 둘러보는 술래 + 첫 아이템 | 무작위 순찰 + CCTV 호출 | 은신처 뒤 점검 + 5곳 중 4곳 |
| 술래 순찰 | P1↔P2 왕복 | 중앙 둘레 루프 L1→L5 | 외곽 루프 P1→P6, 2초 멈춰 좌우 확인 | P·L 무작위 순서 | Lv4 + 은신처 점검 H1~H3 |
| 술래 속도(m/s) | 0.12 | 0.15 | 0.18 | 0.20 | 0.22 |
| 게이지 만충(s) | 3.0 | 2.5 | 2.0 | 1.5 | 1.2 |
| 수색 | 없음 | 3 s 회전 | 마지막 위치 + 은신처 1곳, 6 s | 은신처 2곳, 8 s | 반경 1.5 m 은신처 전부, 10 s |
| 발전기 | G3, G4, G5 · 즉시 | G2, G3, G5 · 3 s | G1, G3, G4, G5 · 4 s | G2~G5 · 5 s | 5곳 중 4곳 · 5 s |
| CCTV | 없음 | C1 | C1, C2 | C1~C3(호출) | C1~C4 |
| 아이템 | 없음 | 없음 | 가속 | 투명, 모래시계 | 전부 |
| 제한 시간 | 4:00 | 3:30 | 3:00 | 3:00 | 2:30 |

Lv1의 술래 속도·게이지·순찰선은 술래 제어 설정에, 제한 시간·하트(3)·사탕·탈출존은 레벨 파일(SR-013)에 둔다. Lv1의 탈출은 사탕 3개를 모은 뒤 탈출존에 들어가면 즉시 성공이며 문 앞 대기 시간은 없다.

용어: P1~P6 순찰 지점, L1~L5 중앙 둘레 루프 지점, H1~H3 은신처, G1~G5 발전기(열쇠) 위치, C1~C4 CCTV 관문. 위치 좌표는 레벨 설정 파일(SR-013)에 둔다.

## 부록 D. 표기 규칙과 인용한 BRD 항목

본문은 요구 연결에 **BR-nn(비즈니스 요구)과 SR-nnn(시스템 요구)** ID만 주로 쓴다. 그 밖에 나오는 표기는 아래와 같다.

| 표기 | 뜻 |
|---|---|
| BR-nn | 비즈니스 요구 (BRD 6장). 아래 표 1 |
| SR-nnn | 이 문서의 시스템 요구. 001~013 구성 요소(§4), 014~025 인프라·데이터·인터페이스(§5), 030~041 안전·신뢰성·보안·유지보수(§7) |
| BA-nn | 비즈니스 인수 항목 (BRD 10장). §9.2에서만 씀. 표 2 |
| 정의서 | 팀 인터페이스 정의서 [interfaces.md](../interfaces.md)(개발팀장 확정, 기준일 2026-10-10). 본문의 "정의서 §n"은 그 문서의 절 번호 |
| 발표 TR-nn | 팀 Notion "오전 발표 준비" 문서의 기술 요구 번호. BRD의 BR과 번호 체계가 다르며 출처 표시로만 쓴다. 대응은 부록 B |
| `[확인]` | 팀이 결정하거나 실측해야 하는 값. 항목은 부록 C |
| `[가정]` | 실측 전에 임시로 둔 값 |
| `[제안]` | 이 문서가 새로 붙인 값. 표기가 없는 값은 팀 Notion에 있는 값 |
