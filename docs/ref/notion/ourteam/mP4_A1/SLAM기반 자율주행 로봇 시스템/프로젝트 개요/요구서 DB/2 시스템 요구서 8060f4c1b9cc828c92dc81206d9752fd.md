## 2.1 System Requirement Method

본 시스템 요구서는 「SLAM·객체 탐지 기반 산업 실내 레이아웃 변화관리 시스템」의 BRD를 구현·검증 가능한 시스템 요구사항으로 전개한다. 승인된 실내 시험 구역에서 RGB-D 영상의 특징점을 활용한 위치 추정, 점군 기반 3차원 지도 생성·갱신·표시, 객체 기록, 회차 간 평면 위치 변화 비교를 검증한다.

**도출·관리 원칙**

- BRD의 BR-T 요구사항을 기능·데이터·성능·인터페이스·품질 요구사항으로 분해하고, SR ID와 검증 ID를 연결한다.
- “필수”는 승인된 프로젝트 범위에서 충족해야 하는 요구사항이다. 요구사항 채택과 구현 달성은 구분하며, 이 문서는 달성 결과를 주장하지 않는다.
- 확정된 사용자 결정, BRD에서 도출한 구현 요구사항, 검증 후 결정할 수치를 구분한다. TBD는 미정이며 인수 시험 전에 값·측정 조건·승인자를 확정해야 한다.
- 외부 연구의 처리 주기, 상용 센서의 깊이 정확도, 스캐너의 형상 정확도는 참고 자료로만 사용한다. 이를 본 시스템의 성능 목표나 기준선으로 전용하지 않는다.
- 기능 검증은 시연·시험으로, 데이터 규약과 설정은 검사로, 성능·업무 부담은 측정·분석으로 확인한다. BRD 변경 시 관련 SR·검증 항목도 함께 검토한다.

**근거의 구분:** 사업 목적과 범위는 상위 BRD 및 확정된 프로젝트 결정을 따른다. 좌표·단위 규약은 ROS REP-103/105, 장비 구성 확인은 TurtleBot4 공식 매뉴얼을 참조한다. 해당 자료는 아래 요구사항 도출의 기술 근거이며, 고객 수요나 본 시스템의 정확도를 입증하는 자료는 아니다. 참고 링크는 2.11에 정리한다.

표 안의 F·D·P·I·Q 번호는 각각 SR-F·SR-D·SR-P·SR-I·SR-Q 요구사항을 줄여 표기한 것이다. KPI 번호는 BRD의 BR-KPI 번호를 뜻한다.

## 2.2 System Context

**시스템 목적과 경계**

시스템은 지정된 조사 구역을 두 로봇이 분담하여 관측하고, 조사 중 위치와 로봇별 3차원 점군 지도를 표시하며, 조사 회차의 지도·객체 기록을 저장한다. 이후 기준 회차와 비교 회차를 공통 좌표계에 정합하여 추가·이동·제거 후보와 판정 근거를 제공하고, 사용자의 검토 결과를 기록한다.

| 외부 요소·사용자 | 시스템과의 상호작용 | 책임·경계 |
| --- | --- | --- |
| 조사 운영자 | 구역·기준 회차·대상 객체 설정, 시작·중단, 진행·실패 확인 | 시험 구역과 통행 조건 확인, 허용된 개입 수행 |
| 결과 검토 사용자 | 회차 조회, 변경 후보와 전후 관측 확인, 판단 기록 | 업무상 변경 여부와 추가 조사 필요성 검토 |
| 현장·대상 객체 | RGB·깊이·거리 관측의 대상 | 관측 가능 조건을 사전 확인; 미관측은 변화의 증거로 간주하지 않음 |
| TurtleBot4 2대와 탑재 센서 | 주행·센서 입력·로봇 상태 제공 | 물리 장비는 프로젝트 자원; 제어·데이터 연결은 시스템 통합 범위 |
| 연산·통신·저장 환경 | SLAM·객체 처리·통합·조회 지원 | 배치 위치와 사양은 시험 결과에 따라 설계에서 결정 |
| 평가·인수 담당자 | 기준 자료·정답표·시험 결과 확인 | 수치·조건 승인 및 인수 판정 |

**목표 업무 흐름:** 사전 점검 및 조사 설정 → 구역 분담 → 조사·실시간 위치/지도 확인 → 결과 저장 및 품질 확인 → 두 로봇 결과 통합 → 기준 회차와 비교 → 사용자 검토 → 회차별 조회·재조사.

로봇별 실시간 점군 지도 갱신·표시는 필수 범위이다. 두 로봇의 최종 결과는 하나의 조사 회차에서 공통 좌표계로 통합한다. 통합 지도까지 조사 중 실시간 갱신·표시할지는 2.3의 미결정 사항으로 관리한다. 실시간 위치 추정은 조사 로봇의 위치에 대한 요구이며, 사람·차량의 순간 위치를 추적하는 요구가 아니다.

**공통 시험 조건:** 장비·모델·배포판·입력 설정·연산 자원·통신 조건·시험 구역·대상 정답·기준 측정·초기 상태·허용 개입·반복 횟수를 고정한다. 인시 비교는 센서 취득 시간만 비교하지 않고 사람의 준비·개입·검토·재조사를 포함한다.

**미달 처리:** 실패 항목·조건·관련 SR·증거를 남기고 원인 분석 후 재시험한다. 조건부 수용 또는 범위 조정은 평가·인수 담당자의 승인과 BRD/SRD 변경 기록이 필요하다. 고객 비용·반복 수요 검증은 사업 검증이며 시스템 기능 시험의 통과와 구분한다.

## 2.11 Boundary to the SDD

SRD는 제공할 기능·정보·품질·외부 계약·시험 조건을 정의한다. 아래 구현 선택은 SDD에서 비교·결정하고 관련 SR을 추적한다.

| SRD에서 정하는 것 | SDD에서 정할 것 |
| --- | --- |
| 영상 특징점 기반 위치 추정, 깊이 기반 3차원 점군 지도, 실시간 출력 조건 | SLAM/오도메트리 알고리즘·노드 구성·연산 배치·루프 폐쇄·점군 필터/해상도 |
| 객체 클래스·대표점 규칙·필수 기록·오차·완전율 | 탐지 모델·학습 데이터·깊이 선택·3차원 대표점 추정·관측 통합 구현 |
| 공통 좌표·정합 품질·회차 비교·판단 불가 처리 | 정합 알고리즘·좌표 변환 관리·객체 대응·변경 판정 처리 흐름 |
| 두 로봇 분담·주행 범위·실패/중단 행동 | 구역 배정·경로 계획·공유 구간 제어·복구 방식 |
| 인터페이스 정보·시각·좌표·오류 의미 | 토픽·메시지/API·QoS·파일 형식·DB 구조·UI 구성 |
| 장비 수·성능 조건·저장/보존·측정 가능성 | PC/GPU 배치·네트워크·용량 산정·배포·로그/측정 도구 |

구현 방식이 성능·범위·데이터 계약을 변경하는 경우 SRD의 영향 항목을 먼저 검토한다. 특정 패키지나 모델을 선택했다는 이유만으로 요구사항 충족을 인정하지 않는다.

**기술 참고 자료**

- [ROS REP-103: 단위와 좌표 규약 원문](https://github.com/ros-infrastructure/rep/blob/master/rep-0103.rst) — SR-D01의 단위·축·광학 프레임 규약 근거.
- [ROS REP-105: 이동 로봇 좌표 프레임 원문](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst) — SR-D02의 map/odom/base_link 의미와 다중 로봇 프레임 구분 근거.
- [TurtleBot4 공식 매뉴얼: Features](https://turtlebot.github.io/turtlebot4-user-manual/overview/features.html) — 교육·연구 플랫폼 및 Standard/Lite의 센서 구성 확인 자료. 실제 보유 모델은 별도 확인한다.
- [RTAB-Map ROS 공식 저장소](https://github.com/introlab/rtabmap_ros) — ROS 통합 구현 후보 자료. 본 문서에서 알고리즘 선택이나 성능 달성을 확정하지 않는다.

사업 필요성·기존 대안·비용의 레퍼런스는 상위 BRD를 따른다. 본 초안에서 추가한 운영·데이터 요구사항은 해당 업무와 시험을 성립시키기 위한 도출 요구사항이며 외부 제품의 보장 성능을 인용한 요구사항이 아니다.
