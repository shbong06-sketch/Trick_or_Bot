# 3. 입력 데이터와 처리 방식

거리 0.5m·1.0m·1.5m별 수집한 rosbag을 사용한다. 각 데이터에는 방향·가림·이동 조건이 포함되어 있다. 재생 배율과 bag별 원본 프레임 수는 제공 로그에 없어 별도 기록이 필요하다.

구독 콜백은 압축 이미지 메시지를 큐에 저장하고, 별도 스레드가 디코딩과 탐지를 수행한다. 대기 큐는 1개이며, 큐가 차면 오래된 메시지를 최신 메시지로 교체한다.

- 동일 클래스의 bbox·confidence·중심 좌표와 원본 header timestamp를 JSON으로 발행한다.
- 첫 predict 호출은 초기화를 포함하므로 시간 집계에서 제외한다. 별도의 충분한 워밍업은 수행하지 않은 간단한 측정이다.

# 4. 시간 측정 범위

**측정값의 명칭: 노드의 프레임 처리 시간**

압축 이미지 디코딩 → Ultralytics predict 호출(전처리·모델 실행·후처리) → 검출 결과 CPU 복사 → JSON 생성 → publish 호출 완료를 포함한다.

화면 표시·bbox 그리기, 큐 대기, 카메라 및 DDS 전송, 결과 구독 노드의 수신 시간은 포함하지 않는다. 따라서 순수 모델 추론 시간 또는 카메라부터 결과까지의 전체 지연으로 표기하지 않는다.

평균은 실행 시작 이후 처리한 프레임의 **누적 평균**이며 30프레임마다 출력한다. 로그의 평균들을 다시 평균하지 않고 마지막 집계값을 실행 요약으로 사용한다.

# 5. PT 거리별 측정 결과

| 거리 | 마지막 집계 프레임 수 | 누적 평균 처리 시간 | 로그상 처리 빈도 |
| --- | --- | --- | --- |
| 0.5m | 630 | 8.97ms | 약 10FPS |
| 1.0m | 750 | 9.57ms | 약 10FPS |
| 1.5m | 600 | 9.50ms | 약 10FPS |

거리 표기는 사용자가 각 로그 아래에 기재한 거리 설명에 대응했다. 프레임 수는 마지막으로 출력된 집계 기준이며 종료 시 최종 총처리 수와 같다고 단정하지 않는다.

로그 시각 기준으로 30프레임 처리마다 약 3초가 경과한다. 0.5m의 30→630프레임은 약 60초, 1.0m의 30→750프레임은 약 72초, 1.5m의 30→600프레임은 약 57초로 모두 약 10FPS다.

# 6. 결과 해석과 한계

- 세 실행의 누적 평균 처리 시간은 약 9~10ms다. 로그상 처리 간격 약 100ms 대비 측정 처리 구간은 짧게 나타났다.
- 이는 현재 입력 조건에서 처리 시간의 여유를 시사하지만, 수신·큐 교체 수가 없어 모든 프레임을 처리했는지는 확정할 수 없다.
- 거리별 최대 평균 차이는 0.60ms다. 영상 내용·집계 프레임 수·실행 시간이 다르고 반복 측정이 없어 거리 자체의 영향으로 해석하지 않는다.
- 1000/처리시간으로 계산한 값을 실제 발행 FPS로 사용하지 않는다. 실제 로그상 처리 빈도는 약 10FPS다.
- Precision·Recall, 오분류·오탐 수, 탐지 끊김은 이 시간 로그만으로 평가할 수 없다.
- 프레임별 기록이 없어 P95·최댓값·지연 분포는 계산할 수 없다. 누적 평균 감소만으로 워밍업 또는 발열 영향을 확정하지 않는다.
- 기존 Tesla T4에서의 약 3.93ms는 측정 장비와 범위가 달라 이번 약 9ms와 직접적인 성능 우열 비교에 사용하지 않는다.

# 7. GPU 상태와 종료 경고

사용자가 제공한 nvidia-smi 스냅샷에는 온도 58°C, 전력 20W/80W, 메모리 701MiB/6144MiB, GPU 사용률 15%가 표시되었다. 다만 목록에 Python 추론 프로세스가 없으므로 이를 실험 중 평균 GPU 사용률·모델 메모리 사용량으로 해석하지 않는다.

1.0m 실행 종료 시 QObject 타이머 관련 경고가 나타났다. OpenCV GUI를 작업 스레드에서 사용하는 구조와 관련될 가능성이 있으나 확정하지 않는다. 속도 비교에서는 PT·ONNX 모두 화면 표시를 끄고 확인한다.

# 8. ONNX 비교를 위한 후속 조건

- 동일 [best.pt](http://best.pt)를 ONNX로 변환하고 실제 ONNX Runtime 실행 provider가 CUDA인지 확인한다.
- PT·ONNX 모두 동일 GPU·입력 크기·confidence·NMS·정밀도·화면 표시 조건을 사용한다.
- 0.5m·1.0m·1.5m의 동일 bag을 동일 배율로 재생하고, 각 실행마다 노드를 재시작해 누적 평균을 분리한다.
- 속도 비교에서는 SHOW_IMAGE=False로 고정하고 동일 워밍업 기준으로 각각 3회 반복한다.
- 최신 프레임 교체 방식에서는 PT와 ONNX가 처리한 원본 프레임이 달라질 수 있다. 본 비교는 실제 패키지 처리 성능으로 해석한다.

# 9. 현재 결론

**RTX 3060 Mobile 환경에서 ROS2 detection 패키지의 PT 실행은 세 거리 모두 약 9~10ms의 누적 평균 프레임 처리 시간을 기록했다. 로그상 처리 빈도는 약 10FPS다.** 탐지 정확도, 전체 지연, 프레임 누락과 ONNX의 개선 효과는 현재 자료만으로 확정하지 않는다.
